# Auditoría del plan maestro de IDsanna

## Resultado
El plan es técnicamente viable, pero no es una sola entrega: son 11 fases con dependencias. La prioridad correcta es un MVP vertical verificable antes de multimodalidad, metadatos dinámicos y Pro.

## Capacidades altas
- Separación cliente/Supabase/Edge Functions/proveedores.
- RAG con aislamiento por usuario y materia.
- Capa multi-proveedor y costes configurables.
- Créditos idempotentes y auditables.
- Modelo educativo multiagente con límites de llamadas.
- Seguridad explícita contra prompt injection.
- Arquitectura móvil empaquetable.

## Riesgos y decisiones
1. **Embeddings**: `document_chunks.embedding` debe conservar 1536 dimensiones hasta aprobar una migración explícita.
2. **Gemini File Search**: puede ser un experimento, no sustituye Supabase como fuente persistente.
3. **APK**: WebView local es la primera shell; Auth, subida y RAG deben pasar por funciones protegidas.
4. **Pro**: no activar pagos por una señal del cliente; requiere proveedor de pagos y webhook verificado.
5. **Opel**: se conserva como metadato configurable hasta definir la norma exacta.
6. **WASM**: no se añade en la fundación; solo si una prueba demuestra beneficio real.
7. **Migraciones**: deben ejecutarse y verificarse en Supabase; la existencia del archivo no prueba aplicación.

## Criterio de salida de la primera fase
Auth real, perfil, creación de materia con RLS, navegación Android, contrato de Edge Function y CI reproducible. Sin datos falsos ni claims de RAG terminado.

## Secuencia
Fundación → materias → chat → RAG → importaciones → evaluación → créditos → metadatos → analítica → Pro → APK endurecida.
